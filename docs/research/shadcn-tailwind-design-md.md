# Current shadcn/ui, Tailwind CSS, `cn`, and DESIGN.md guidance

Checked against first-party sources on 2026-09-04.

## Recommended setup for this repository

The current shadcn Vite path uses Tailwind CSS v4. Install `tailwindcss` and
`@tailwindcss/vite`, add `tailwindcss()` to the existing Vite plugin list, and
import `tailwindcss` from the app's global stylesheet. The shadcn guide also
adds an `@/*` TypeScript path and matching Vite alias before running
`pnpm dlx shadcn@latest init`. See the [shadcn Vite guide](https://ui.shadcn.com/docs/installation/vite)
and [Tailwind's Vite guide](https://tailwindcss.com/docs/installation/using-vite).

Applied to this repository's shape:

- Keep the existing `react({ compiler: true })` configuration and append
  `tailwindcss()` in `vite.config.ts`.
- Add `paths: { "@/*": ["./src/*"] }` to the existing single `tsconfig.json`.
  The two-file edit in the shadcn example only applies to the split tsconfig
  generated by Create Vite. This repository already uses TypeScript 7, which
  removed `baseUrl`; the path mapping resolves from the config file without it.
- Add the matching `@` to `vite.config.ts`. The documented `path.resolve` setup
  requires `@types/node` as a development dependency; Vite 8's native config
  loader uses `import.meta.dirname` instead of the guide's `__dirname`.
- Point `components.json.tailwind.css` at `src/styles.css`, set
  `tailwind.config` to `""`, use `rsc: false`, `tsx: true`, and keep
  `cssVariables: true`. Tailwind v4 configuration belongs in CSS, so a
  `tailwind.config.ts` file would add a second, obsolete configuration path.
  The fields and the blank v4 config are specified in the
  [components.json reference](https://ui.shadcn.com/docs/components-json).
- Run `pnpm dlx shadcn@latest init --base base` after the Tailwind and alias
  setup. Base UI is already the default, but the explicit flag records the
  intended primitive family. Add only the components the application uses
  with `pnpm dlx shadcn@latest add <component>`.

Current `init` adds `cn`, `shadcn`, `class-variance-authority`,
`tw-animate-css`, the selected icon package, and the selected primitive
package. Choosing Base UI adds `@base-ui/react`; choosing Lucide adds
`lucide-react`. The official registry builds this dependency set from the
selected base and preset, rather than asking applications to install every
primitive up front. See the shadcn source for
[base definitions](https://github.com/shadcn-ui/ui/blob/main/apps/v4/registry/bases.ts)
and [registry base construction](https://github.com/shadcn-ui/ui/blob/main/apps/v4/registry/config.ts).

The generated stylesheet begins with:

```css
@import "tailwindcss";
@import "tw-animate-css";
@import "shadcn/tailwind.css";
```

`shadcn/tailwind.css` supplies shared Tailwind v4 state variants and accordion
animations, which is why current `init` keeps the `shadcn` package installed.
It can be inlined with `shadcn eject`, but that is irreversible and gains
nothing for this application. See the [CLI eject documentation](https://ui.shadcn.com/docs/cli#eject).

One visual-parity trap needs an explicit decision. `@import "tailwindcss"`
automatically includes Preflight, and Preflight is built on `modern-normalize`.
This application previously imported `modern-normalize` separately. The
migration follows the standard shadcn path: use Preflight, remove the duplicate
import, and restore required legacy base rules explicitly. Tailwind also
documents how to omit Preflight if retaining an older reset proves necessary. See
[Tailwind Preflight](https://tailwindcss.com/docs/preflight).

## Theme and design-token implications

Shadcn recommends CSS variables. Values live under `:root` and optional
`.dark`; `@theme inline` exposes them as utilities such as `bg-background`,
`text-foreground`, `border-border`, and `ring-ring`. Background tokens pair
with `-foreground` tokens. The full convention is in the
[shadcn theming guide](https://ui.shadcn.com/docs/theming).

For this migration, generated theme values are a scaffold, not a new visual
design. Map the existing surfaces, text, borders, controls, focus ring,
radius, type, spacing, and motion into semantic variables. Keep the existing
local Inter and Fraunces files. The current Nova preset selects Geist, so its
font dependency and import would change the design if left in place. The
official preset mapping is visible in
[shadcn's registry configuration](https://github.com/shadcn-ui/ui/blob/main/apps/v4/registry/config.ts).

If the implementation uses nearby Tailwind palette values, put them behind
the semantic variables rather than scattering palette utilities through
components. For example, map `--primary` to a chosen Tailwind color variable,
then keep component code on `bg-primary` and `text-primary-foreground`.

Tailwind v4 theme variables are the actual Tailwind configuration. Namespaces
such as `--color-*`, `--font-*`, `--radius-*`, `--ease-*`, and `--animate-*`
create matching utilities; keyframes may live inside `@theme`. Use `:root`
for variables that should not create utilities. See
[Tailwind theme variables](https://tailwindcss.com/docs/theme).

Do not assume shadcn's default animations preserve the current application
motion. Keep the existing view-transition durations, easing, keyframes, and
reduced-motion rules, then expose only repeated values as Tailwind theme
variables. `tw-animate-css` and `shadcn/tailwind.css` cover component utility
needs, not the application's full motion language.

## What "base" means

These settings sound similar but control different things:

| Term | Example | Meaning |
| --- | --- | --- |
| Component base | `shadcn init --base base` | Selects the Base UI primitive implementation and installs `@base-ui/react`. Current alternatives are `radix` and `aria`. The CLI calls the Base UI option simply `base`. |
| Base color | `tailwind.baseColor: "neutral"` | Seeds default theme colors. It does not select Base UI. Current choices are Neutral, Stone, Zinc, Mauve, Olive, Mist, and Taupe. |
| Style | `style: "base-nova"` | Selects the component template/preset. `base-nova` means the Nova style built on Base UI. It also carries preset choices such as icon and font. |

Shadcn made Base UI the default primitive family in July 2026 and still
supports Radix. See [Base UI as the default](https://ui.shadcn.com/docs/changelog/2026-07-base-ui-default),
the [CLI option reference](https://ui.shadcn.com/docs/cli#init), and the
[base-color reference](https://ui.shadcn.com/docs/theming#base-colors).

## `cn` usage and status

The recommended `shadcn-ui/cn` package is now the official shadcn default,
not an adjacent community utility. Since September 2026, registry components
import `cn` directly from `"cn"`; `shadcn init` installs it and leaves
`src/lib/utils.ts` as a one-line compatibility re-export:

```ts
export { cn } from "cn"
```

Do not also install `clsx` and `tailwind-merge`. For a project that already
has the old helper, `pnpm dlx shadcn@latest migrate cn` rewrites supported
imports and removes the old packages when no references remain. See the
[shadcn cn announcement](https://ui.shadcn.com/docs/changelog/2026-09-cn)
and [migration reference](https://ui.shadcn.com/docs/cli#migrate-cn).

The package's own README says it is ready for use, has no runtime
dependencies, matches the familiar conditional-class and Tailwind-conflict
APIs, and supports Tailwind CSS v4. Tailwind v3 projects should stay on
`tailwind-merge` v2. Standard use needs no configuration; `cn/config` only
matters if this project later defines custom class-conflict groups or a
Tailwind prefix. See the official [`shadcn-ui/cn` repository](https://github.com/shadcn-ui/cn).

The package is new and still pre-1.0. The npm `latest` tag was `0.2.5` when
checked, while the install environment's release-age policy currently resolves
the compatible `0.2.4`. Keep that resolved version in `pnpm-lock.yaml`; the
normal age gate can admit the newer release without a policy exception. See the
[npm package record](https://www.npmjs.com/package/cn).

## DESIGN.md requirements

The Google specification is currently `alpha`. A DESIGN.md file has optional
YAML front matter for machine-readable tokens and a Markdown body for design
rationale. If front matter is present, use `version: alpha`, give the system a
`name`, and keep supported token groups under `colors`, `typography`,
`rounded`, `spacing`, and `components`. Colors accept CSS values including
hex and OKLCH; dimensions accept `px`, `em`, and `rem`; token references use
`{path.to.token}`. See the [full format specification](https://github.com/google-labs-code/design.md/blob/main/docs/spec.md).

Known prose sections should use `##` headings in this order:

1. Overview
2. Colors
3. Typography
4. Layout
5. Elevation & Depth
6. Shapes
7. Components
8. Do's and Don'ts

Tokens hold exact values, while prose explains where and why to apply them.
Google's accompanying philosophy goes further: a concrete visual reference,
behavioral guidance, and a short list of negative constraints carry more
design intent than a large token inventory. See
[PHILOSOPHY.md](https://github.com/google-labs-code/design.md/blob/main/PHILOSOPHY.md).

Motion is not a first-class front-matter token group in the alpha schema.
Document animation durations, easing, view transitions, component state
motion, and `prefers-reduced-motion` behavior in prose under Components or in
a clearly named custom section. Consumers must preserve unknown sections;
inventing animation properties inside `components` instead produces linter
warnings because the recognized component properties are limited.

Validate the root `DESIGN.md` with:

```sh
pnpm dlx @google/design.md lint DESIGN.md
```

The CLI can also export Tailwind v4 variables with
`export --format css-tailwind`, but that output only translates the formal
token groups. It cannot replace the hand-authored shadcn semantic mapping or
the prose-only motion rules. The CLI and the alpha status are documented in
the [official README](https://github.com/google-labs-code/design.md#readme).
